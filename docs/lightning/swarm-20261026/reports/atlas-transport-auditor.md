## Findings

**F1. Fork vs original: exactly one change, with side effects.** `diff -u` shows the only edit is in `requestPath()` (original lines 72–79): the fork returns `''` when `url.origin !== window.location.origin` (fork lines 75–80). Behavioural consequences: (i) cross-origin `.geojson` passes to native fetch (fork A1: 200, 408 features, counters unchanged); (ii) same-origin `.geojson` is still captured (fork B3: synthetic 200 then body error, `intercepted_on_demand +1`); (iii) the map-ready branch (lines 281–285) no longer fires for cross-origin paths — original A5 counted `map_ready_requests +1` and applied `cache:'force-cache'` to `…/data/airports.geojson` on raw.githubusercontent.com, the fork did neither; (iv) behaviour now depends on where the page is served: `DATA_BASE` (line 5) is same-origin on ventusltd.github.io but cross-origin on any preview/local host; (v) `GENERATION` stays `'202609241251'`, so the fork's runtime state misreports its identity; (vi) the new SHA (`fa1c05e0…`) forces a new `current.json` generation — the original is no longer byte-for-byte. Evidence: E/bridge-diff-original-vs-fork.diff; results.json `compositions.fork.suite`.

**F2. Why `.geojson` is captured, with line numbers.** `requestPath()` (72–79) takes a string or `input.url`, resolves against `window.location.href` and returns only the pathname (host dropped). `mapReadyKey()` (81–86) matches the 11 `/data/<name>` basenames (11–23). `legacyStem()` (88–94) lower-cases the basename and returns a stem for `repd_master.json`, `heavy_emitters_uk.json` or anything ending `.geojson`; `window.fetch` (277–330) passes through only when the stem is empty (line 287). It is basename-only and origin-blind because the engine's own URLs are root-relative (`/uk_metros_trams.geojson`, `/dist/repd_master.json`, `/heavy_emitters_uk.json`, shell index.html; `TRANSIT_URLS` engine line 69). Captured requests never reach the network: a 200 `Response` with `X-GridAtlas-Data-Plane`, `Content-Type: application/geo+json`, `Cache-Control: private, max-age=3600` is returned at once (322–329) while `queryOnDemand()` runs; a foreign stem fails at `resolvePartition()` (224). Proven: A1 string, A2 `Request`, A4 `.GEOJSON?v=1#frag` → status 200 in 0.2–3.4 ms, body rejects, `intercepted_on_demand/streamed_responses/failures/stream_failures` each +1, and CDP shows **no request** to the feed URL for any of them (network-cdp.jsonl; server-access.log shows no hit for bare `sample.geojson`, `repd_master.json`, `heavy_emitters_uk.json` — B3/B4/B5). Passthrough proven for `.json` (B1 raw host 200/49,101 B; B2 local; B6 `.json?file=x.geojson`; all counter deltas 0).

**F3. Input types: strings and `Request` are captured; `URL` objects are not.** `input?.url` is `undefined` for a `URL` object (line 74), so it resolves to `…/atlas/undefined` and passes through with the init intact: A3 `fetch(new URL(feed))` → real network, 200, 215,536 B, 408 features, counters 0. This is an accidental property-miss, not a contract; it must not become the implant's transport (see Recommendation).

**F4. Nothing but `window.fetch` is touched.** Boot checks: `XMLHttpRequest.prototype.open/send`, `EventSource`, `Worker` all `[native code]`; only `fetch` is not. C1 XHR to the feed: 200, 215,536 B. C2 XHR, C3 Worker-fetch (worker `fetch.name === 'fetch'`), C4 Worker-fetch to the feed, `<img>`, `EventSource` (`Accept: text/event-stream`), `<link rel=preload as=fetch>` all hit the server (server-access.log 16:58:11.838–12.001). MapLibre 3.6.2 fetches a GeoJSON-source URL inside its worker (`_updateWorkerData` → `actor.send('geojson.loadData')` → worker `getJSON`; dev build lines 37412–37420, 34305–34312, read from another lane's npm fixture), so `addSource({data: url})` would also bypass the wrapper — consistent with the bridge's own `critical_400kv_maplibre_worker_source: true` (line 36).

**F5. The capture is already in production under a misdiagnosis — and the fix the authors shipped is XHR.** `202609241334-sld-sandbox-v9-8.js:8199` loads `../../data/interconnectors.geojson`; its comment (1900–1902) and `202609071213-place-global-search-v9-5.js:330–333` say "the composer executes cartridges from a blob: origin, where fetch resolves 200 and then throws TypeError reading the body … measured twice", and both use XMLHttpRequest. That symptom is F2 plus a Chromium trait I verified in isolation: `Response.text()/json()` on an author-errored stream rejects with a generic `TypeError: Failed to fetch` whatever the reason object (E/results-chromium-stream-error-surface.json); only `body.getReader().read()` shows the bridge's `AbortError`/`no V9 Parquet partition…`. So a captured `.geojson` is indistinguishable, at the call site, from a network failure — which is how the V5 preview (`weather-module.js:12,125`: `fetch(DATA_URL,{cache:'no-store'})` on the `.geojson`) came to need the fork.

**F6. The original composition already fetches `.json` from raw.githubusercontent.com with plain fetch.** `202609062358-substation-intelligence-v9-63.js:8349`: `fetch(PRODUCT, { cache: 'no-cache' })` where PRODUCT is `https://raw.githubusercontent.com/Ventusltd/data-grid-gb/<commit>/derived/connection-points.v3.json` (4046–4056); observed in the boot network log of the original. The bridge's own proof asserts an unrelated `.json` reaches native fetch (`tools/proofs/202609241251-streaming-parquet-bridge.proof.mjs:98–100`). The PR #1 loader (`history-window.mjs:100,106`) and `history.py:5–7,35,54` already chose `.json` shard names for this exact reason.

**F7. Host behaviour (d).** raw.githubusercontent.com: `access-control-allow-origin: *`, `cross-origin-resource-policy: cross-origin`, `cache-control: max-age=300`, `expires` +5 min, `etag` (64-hex, opaque — not the body's sha256 `dbadcb50…` nor the git blob), `content-type: text/plain; charset=utf-8`, `x-content-type-options: nosniff`, Fastly `x-cache: HIT`, `source-age` up to 163 s, **no `Access-Control-Expose-Headers`** (E/curl-raw-geojson-headers-*.txt). In the browser only `cache-control, content-length, content-type, expires` are readable; `etag` is `null` from both fetch and XHR (B1, C1). A hand-written `If-None-Match` header triggers a preflight that the host answers **403** (E/curl-raw-options-preflight.txt; D9 → `net::ERR_FAILED PreflightInvalidStatus`). But the browser revalidates by itself: `cache:'no-cache'` sent `If-None-Match: W/"…"` and received **304** (D3 for the `.json`, D6 for the feed, D8 locally; CDP `responseReceivedExtraInfo.statusCode 304`), while default caching served the second request from disk cache with no network (D2 `fromDiskCache:true`, 2.5 ms). `no-store` re-downloaded 49 KB/215 KB every time (D4). Implication: with the collector cron `20 */3 * * *`, `no-cache` gives ≤~5 min staleness (edge + browser revalidate within 300 s) at the cost of a 304 round-trip; default caching adds up to 5 more minutes; `no-store` adds bandwidth, not freshness, because the Fastly edge still serves for 300 s.

**F8. Abort and timeout (e).** Pre-aborted `init.signal` on a captured URL rejects synchronously with `AbortError: Aborted` (line 290; E1, 0.2 ms; `intercepted_on_demand +1`, `streamed_responses 0`). Abort after headers errors the body via lines 299–303: fresh-page body rejection at 3.8 ms vs 254 ms when the signal is carried only on a `Request` object, which the bridge ignores (`init?.signal`, lines 290/303/308; E/results-abort-fresh-pages.json) — surfaced in Chromium as `TypeError: Failed to fetch` either way (F5). The engine's `fetchWithTimeout` (engine 656–665) clears its 15 s timer at headers; captured headers arrive in <4 ms, so its timer never protects the body. Passthrough `.json` has native semantics: 1 s AbortController on a 5 s endpoint → `AbortError` at 1000 ms (E4); pre-abort → native `AbortError` (E5). Pre-existing note: `getManifest()` (103–117) memoises a *rejected* promise — after one manifest failure every later legacy load fails in <1 ms (second request 0.9 ms, E/results-abort-fresh-pages.json) until reload; unrelated to lightning if the implant never sends `.geojson` through fetch.

**F9. Unreachable host (f).** `.json` → fetch rejects `TypeError: Failed to fetch` after 32 ms, CDP `ERR_TUNNEL_CONNECTION_FAILED`, counters 0 (F1 case). `.geojson` → **status 200, ok:true**, bridge headers, then body `TypeError` — the DNS/connection layer is never exercised and `__GRIDATLAS_MAP_READY__.failures` gains an entry (F2 case; 9 entries after the run, `bridgeStateAfter.failures`). XHR → status 0 / onerror (F3). A `.geojson` consumer therefore cannot tell "host down" from "data plane error".

**F10. Integrity.** A sha256 pin of a feed that changes every 3 h is counterproductive: it fails closed within one cycle, and a pin fetched from the same origin adds nothing. The owner's doctrine (`substation-intelligence` 3998–4040: commit ref + sha256 + byte length, "moving a pin is a cut"; "absent crypto is not a mismatch", 4085–4096) applies to immutable derived products, not observational live data. ETag is usable only through the browser cache (F7). Right pattern: an index/manifest with `generated_utc` (PR #1 `history.py:243`, consumed at `history-window.mjs:113`) plus `latest_detection_utc` as the displayed last-updated; optional `sha256`+`bytes` only for closed-day shards older than the collector's merge window, verified with the existing absent-crypto policy, never for the live feed or the current day.

**F11. Pre-existing / environmental.** Locally the bridge's manifest host was refused, so every legacy on-demand layer would show FAIL in this harness — BLOCKED_DEPENDENCY, not a candidate defect. The brief's `loop.mjs lint` failure is pre-existing on main (not re-run here).

## Objections to other lanes
1. Builder: do not adopt the fork's origin gate "because it is five lines" — it edits an original cartridge, re-hashes `current.json`, changes map-ready classification off-host, and is unnecessary (F2, F6).
2. Anyone citing the cartridge comments about blob: origins: that diagnosis is wrong (F5); plain `.json` fetch works from cartridges today (F6).
3. Data/collector lane: `cache:'no-store'` (preview and PR #1 loader) buys no freshness over `no-cache` and costs 215 KB per poll (F7); do not propose a sha256 pin of the live feed (F10).
4. Visual-parity and menu lanes: with lightning OFF the implant must issue **no** request to the feed at boot — the network waterfall and `__GRIDATLAS_MAP_READY__` counters must be identical to the original; fetch only on first toggle ON.
5. Any lane asserting `__GRIDATLAS_MAP_READY__.failures.length === 0` on the live page after enabling lightning: true only if the implant never routes a `.geojson` or the two reserved `.json` basenames through `window.fetch` (F2, F9).
6. Harness: a black map and FAIL badges locally are BLOCKED_DEPENDENCY (jsdelivr, ventusltd.github.io refused), not evidence about the candidate.

## Recommendation for the smallest additive integration
Transport: plain `fetch(absoluteUrl, { cache: 'no-cache', signal })` of **`.json`-named** resources — `data/history/index.json` and `days/YYYY/MM/DD.json` from PR #1 (GeoJSON inside; basenames must not be `repd_master.json`/`heavy_emitters_uk.json`) — then `response.json()` → `source.setData(featureCollection)`, mirroring the engine's own fetch→setData path and the existing `.json` precedent at line 8349. Build URLs with `new URL(path, indexUrl)` or absolute strings: the composer injects `<base href>` to the release folder (loader line 52), so bare relative paths resolve there (B7). Use an AbortController ~15 s like the engine; on failure fail open to a visible "feed unreachable / no data" state (never zero flashes). Poll no more than every 5–15 min or on toggle; rely on browser revalidation (304s) instead of manual ETag handling, which is impossible here (F7). Freshness/provenance label from the index's `generated_utc` and `latest_detection_utc`.

Until the `.json` shards are published, the only correct ways to read today's `uk_lightning.geojson` are XMLHttpRequest (precedent in two live cartridges, F5) or having the collector publish a `.json` twin; do **not** use the `URL`-object quirk (F3) or MapLibre `data: url` (which hides the payload the UI needs for honest counts/labels). There is no "namespaced alias" the bridge honours — matching is basename-only (F2), so the extension *is* the namespace.

This needs **zero bytes changed** in the original bridge: B1/B2/B6/D1–D8 ran against the untouched `60be8215…` cartridge with every bridge counter at delta 0, and the same path serves `connection-points.v3.json` in the live product today. The fork is the only alternative on the table and it is strictly larger (one cartridge edit plus a `current.json` generation) with no transport benefit (F1).

## Verdict
PASS for the transport lane: `.json` passthrough, XHR and Worker bypass are proven in-browser against the untouched original bridge; the fork is unnecessary. (a)/(d) on raw.githubusercontent.com were reachable; the map itself is BLOCKED_DEPENDENCY locally (jsdelivr, ventusltd.github.io refused), which does not affect these conclusions.
