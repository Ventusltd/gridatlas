Read-only throughout; both clones untouched (`git status` clean). Server: `python3 -m http.server 8110 --directory /home/claude`, killed at the end.

## Scope
Load/boot/heap/long-task budget of the ORIGINAL composition (202609241334) and the REJECTED preview at 393x852 and 360x740 Android-Chrome emulation (4x CPU throttle as the phone-class proxy) and 1440x900 desktop; the measured cost of the preview's lightning path; a MapLibre 3.6.2 rendering budget (circle vs symbol, cluster vs raw, replace vs incremental); collector archive growth and GitHub history bloat; the mobile constraints the implant must honour.

## Findings

**F1. Original boot budget on a phone-class CPU is already heavy; lightning must add nothing to the boot path.** `E/shim/original-393x852-cpu4x.json`: composer written 1.9 s, 60+3 controls 7.3–8.3 s, native menu installed 12.7 s, all 11 preload layers `[OK]` 18.8 s; 43 long tasks totalling 17.4 s (max 1,889 ms); 360x740: menu 12.4 s, 44 long tasks / 18.8 s (max 1,608 ms). Desktop 1x: menu 4.9 s, first frame 6.2 s, 29 long tasks / 4.9 s. Heap after settle 19.9–20.0 MB (CDP) / 22.0 MB (`performance.memory`), 2,479–2,494 DOM nodes. Boot variance at 4x is wide (menu 7.2–12.7 s across runs) — the sandbox has 2 cores.

**F2. Bytes by type at boot (original, shim, uncompressed; `E/shim/original-1440x900-cpu1x.json` `by_type`/`biggest`).** 32 requests, 10.99 MB: Fetch 20 req 10.14 MB (preload GeoJSON 7.71 MB parsed on the main thread by `ventus-corev8engine.js:656-677,1431` — grid_132kv 2.84 MB, industrial_offtakers 1.30 MB, grid_substations 1.19 MB fetched twice …; the four cartridges 0.94 MB; current.json 49 KB; shell 21 KB), Script 763 KB (maplibre-gl.js), Stylesheet 79 KB, plus `connection-points.v3.json` 221 KB gzip on the wire / 2.90 MB decoded, fetched, SHA-256-verified and parsed at install by `202609062358-substation-intelligence-v9-63.js:8345-8359` (pin at 4049-4056). Not counted by page-level CDP: the 400 kV source the MapLibre worker fetches itself (1.47 MB raw / 320 KB gzip, engine line 1240-1243). Realistic wire estimate with GitHub Pages gzip (`gzip -6` of the same files): ≈2.6 MB before DuckDB; DuckDB adds `duckdb-eh.wasm` 35,659,694 B (7.09 MB gzip; the "35.7 MB query engine" of `current.json:362`) + worker 760 KB (186 KB gzip) + the `+esm` bundle, started after `src-400` is loaded (`202609241251-streaming-parquet-bridge-v9-5.js:184-210`, `requestIdleCallback` with a 2 s timeout). **F4. Pre-existing phone risk in the original composer, not lightning.** Chromium logs on every load: *"A parser-blocking, cross site (i.e. different eTLD+1) script, https://cdn.jsdelivr.net/npm/maplibre-gl@3.6.2/dist/maplibre-gl.js, is invoked via document.write. On a 2G-class effective connection with a cold cache Chrome drops that script and the page shows the fatal banner. Pre-existing on main; outside this lane's remit to fix, but every lightning design that adds a second cross-site parser-blocking script inherits it.

**F5. So the lightning JavaScript costs ~0.3 s at phone CPU today; the frame cost is a property of the whole composition and of this renderer.

**F7. MapLibre rendering budget (exact 3.6.2 build; `E/bench-maplibre-cpu4x.json`, `-cpu1x.json`; phone portrait 393x852@3x; software GL so absolute render times are indicative, ratios are the signal).** Time to map `idle` at 4x CPU, circle layer, real shape: 1k 1.2 s; 10k 2.4 s; 40k 6.0 s (long tasks 4.6 s, max 1.8 s); 100k 26.8 s (long tasks 18.1 s, max 9.5 s); CDP heap 27 MB at 10k, 84 MB at 40k. Desktop 1x: 10k 1.1 s, 40k 3.9 s, 100k 9.7 s. `setData(url)` (worker fetch+parse): 40k 5.4 s at 4x — it removes the main-thread stringify but not the tile build. `updateData({add:400})` on 40k: 6.7 s versus full replace 7.5 s (1x: 4.7 vs 5.1 s) — the worker re-indexes and re-tiles the whole set either way, so incremental refresh is only a main-thread saving (≈1 s at 40k real shape), never a render saving. `cluster:true` (radius 40, maxZoom 11): 40k 1.4 s, 100k 3.0 s at 4x, 52–56 clusters on screen, zoom step 0.7–0.8 s versus 2.5 s for 40k raw circles. Symbol layer with an icon and collision (no text — glyphs unavailable offline, and text is costlier still): 10k 7.5 s, 40k 25.2 s, 100k timed out at 120 s with nothing rendered (also at 1x); zoom step at 40k 12.1 s versus 2.5 s (circles) and 0.8 s (clusters). Lean shape halves parse/transfer but not tiling: 40k lean 10.2 s / 100k 14.4 s at 4x (variance between runs is ±40 %).

**F8. Archive growth.** Real feed: 525.5 B/flash raw (a ~150-character product-name id plus six constant-text properties per feature, `collect.py:48-67`), 31.5 B/flash gzip; the file is one line, so GitHub shows every refresh as `+1 −1` and the diff is unreadable (`gh api …/commits/<sha>` `stats`). Every successful run commits even with zero new flashes because `query_start_utc/query_end_utc` change each run (`collect.py:210-211`): six consecutive commits 25 Oct 11:33 → 26 Oct 13:07 carried identical 215,536-byte files. PR #1 makes this permanent: `index.json.generated_utc` changes every run (`history.py` index block) and the workflow stages `data/history/` (`update-lightning.yml` diff), so one commit per run is guaranteed: 2,920/yr nominal, ~1,750/yr at the observed 4.8 runs/day (16 scheduled runs in 3.35 days; cron drift). Day-shard, per-period transfer and one-year tables are in `E/archive-model.md`; worst cases from literature-class storm days (28 Jun 2012 ≈110k CG strikes, 26–27 May 2018 ≈60k, times ~3.2 total flashes per CG at 52° N after Price & Rind 1993 — citations from memory, unverifiable from this container): a 60k-flash day = 31.5 MB shard, a 300k-flash day = 158 MB, i.e. **PR #1's uncapped shard exceeds GitHub's 100 MB hard limit on exactly the day the data matter, and the push fails** (every later run then queues behind the same failure). The 7-day feed at its own cap is 21 MB raw / 1.26 MB wire per toggle. Measured packfile growth (`E/sim-git-growth.json`, synthetic bytes, real write pattern, one simulated month ×12 after `git gc` / `gc --aggressive`): main today at 3,000 flashes/day → 297 / 95 MB per year; PR #1 layout → 283 / 150 MB per year (day shards 1.6 MB); lean shape + sealed shards + commit-only-on-change → 148 / 49 MB; the 40k-cap saturation regime (45,714/day, 5 simulated days ×73) → main 1.2 / 0.86 GB per year, PR #1 1.9 / 1.2 GB per year with 24 MB day shards. GitHub's server packs behave like the default column, not the aggressive one.

**F9. Per-session transfer by period choice (`history-window.mjs` semantics).** ≤31-day windows download every overlapping shard (4 concurrent, `cache:'no-store'`) and apply the 40k cap only after download; `cachedDays.clear()` on every 3-hourly index revision defeats the in-memory cache. Summer-active (3k/day): 7d ≈ 0.76 MB wire / 12.6 MB parsed; 30d ≈ 2.9 MB / 48.9 MB parsed before capping. Severe (60k/day): 7d 15 MB / 252 MB — a phone cannot parse that. 3m–12m are index-only (~15 KB gzip at 365 days): correct.

## Objections to other lanes
- **Transport**: a `.json` suffix that passes the bridge is necessary but not sufficient. If the implant then does `fetch → res.json() → setData(object)` on the main thread it pays parse + stringify + worker parse (F6). The budget path is `addSource({type:'geojson', data: '<https://raw…/*.json>'})`: MapLibre's worker fetches and parses it, nothing touches `window.fetch` (the bridge hooks only `window.fetch`, `202609241251-…:277`; the original already uses this path for the 400 kV source, bridge `architecture.critical_400kv_maplibre_worker_source:true`). `cache:'no-store'` must not be copied onto sealed shards; raw.githubusercontent.com serves `cache-control: max-age=300` and the Tracker's `?t=Date.now()` cache-busting pattern would defeat it.
- **Time-window UX**: the cap must be decided from `index.json` counts *before* any shard is fetched; 30d detail on a phone is only safe when the index sum is below the cap. "Shown of archived" labels are right; add "downloaded".
- **Archive**: the feature shape is the root cost (527 B vs 121 B). Uncapped daily shards plus rewrite-every-run is the growth bug; sealed shards plus a lean shape fix both.
- **UI/menu guardian**: the preview prepends a Weather group into `#scada-ui-container` and `#fs-curtain-keys` at install even when OFF (`weather-module.js:71,104`, +14–17 nodes); every status text change fires the menu bar's body-wide `MutationObserver` (`202609031958-menu-bar.js:1739-1744`) → `adoptLate`+`syncAll` over 63 controls — cheap today, not with per-flash label updates.
- **V5 proof**: `tools/proofs/uk-lightning-preview.browser.mjs:30-50` substituted a 2-feature fixture for the feed; it never exercised a real payload, time or memory.

## Recommendation for the smallest additive integration (budget view)
1. One additive cartridge, nothing at boot: no fetch, no source, no DOM until the user opens the control; the control itself is one 44 px row.
2. Source = `data: <url ending .json>` (worker-fetched, bridge-invisible), circle layer only, `visibility:'none'` until on; never a symbol/text layer (F7, `label_glyphs`).
3. Refresh in place with `updateData({add, remove})` keyed on feature `id` (MapLibre 3.6.2 `GeoJSONSource.updateData`, `maplibre-gl-dev.js:37322-37325`) for the 3-hourly tick; full `setData` only on a period change.
4. Display cap per period on a phone (coarse pointer or ≤700 px): 12h/24h/48h/7d ≤ 10,000 points; above that switch to `cluster:true` (clusterRadius 40, clusterMaxZoom 11) rather than refusing; 30d: points only when the index sum ≤ 10,000, else clusters, else daily counts; 3m–12m: counts only. Desktop may take 40,000 raw but should cluster above 20,000. Justification: a phone budget of ≤2.5 s to idle, no single task over 1 s and ≤30 MB of heap is met by ≤10k raw circles (2.4 s, max task 0.76 s, +7 MB) and by clusters at any N measured (≤3 s at 100k); 40k raw costs 6 s with 1.8 s blocks and +24 MB, and symbols fail above 10k.
5. Collector: lean feature shape (`id` = `<product-ordinal>:<index>` or hash, `properties:{t}`; constants move to `metadata`), sealed day shards written once after the UTC day closes, run metadata in an uncommitted or tiny separate `status.json`, commit only when a feature set changed, hard day-shard ceiling (e.g. 20,000 points per file, overflow into `-part2.json` listed in the index) so no file approaches 50 MB. Repository thresholds: warn at 250 MB packed, act at 500 MB: squash the data branch (orphan rewrite of `data/history` to sealed shards only, or move months older than 90 days to a GitHub Release asset and keep the index pointing at them). Target: lightning repository under 500 MB at year one even in a stormy year.

## Verdict
**FAIL** (for the preview as a budget design: an uncapped 40k `setData(object)` path costs 27 s of long tasks and +24 MB on a phone, and PR #1's uncapped daily shards break on a severe storm day); the ORIGINAL baseline itself is PASS-with-caveats (pre-existing 17–19 s of long tasks at phone CPU and the document.write CDN risk). DuckDB prewarm and tiles: BLOCKED_DEPENDENCY.
