## Findings

**1. FAIL (plan-changing) — the collector has never scanned ~46% of the time since the seed, and nothing records it.** cron `20 */3 * * *` (update-lightning.yml:4) should give 8 runs/day; GitHub actually started 4, 5, 5 scheduled runs on 23–25 Oct, 5–141 min late (EV/actions_runs.txt). Each run fetches only `[now-3h, now)` (collect.py:203-205) with no lookback to the previous successful end. Union of all successful windows: 94.84 h of a 134.4 h span; after the 48 h seed window only 46.8 of 86.4 h (54%); 14 gaps of 1.3–5.3 h (EV/scan_windows_analysis.txt). Per UTC day: 23 Oct 50% scanned, 24 Oct 60%, 25 Oct 60% (EV/per_day_coverage.txt). The feed keeps only the last window (collect.py:210-211), so no consumer can see this. Also 15 of 17 runs examined one product fewer than the 10-minute slots their window overlapped: the slot containing `now` is not yet published, so every window's tail is unobserved yet recorded as scanned (PR history.py:268-273 records `[beginning, now)` verbatim). The PR's `scan_windows` merge (history.py:103-127) would expose gaps but does not close them. The "7-day seed" is really flashes from 21 Oct 12:32 to 25 Oct 11:15 UTC (408 features: 31/67/189/118/3 per day) over half-scanned days.

**2. FAIL — per-day "scanned with no flashes" and "never scanned" are indistinguishable, and uncollected periods print as 0.** history.py:200-201 `if not records: continue`: index.days lists only days with flashes. PROBE 1 (EV/probe_history.txt): a day scanned 00:00–24:00 with zero flashes and a day never scanned both have no entry and no shard; only `scan_windows` differs, and the client never consults it (history-window.mjs:75-80, 141-147). Client label for a never-collected June: "0 flashes recorded on overlapping UTC dates" (PROBE B, EV/probe_client.txt). `cutoff_date_utc` is always now−1y (history.py:146) and the loader gates only on it (history-window.mjs:137-140); a 12m selection over the 5-day seed returns `dailyCounts` for 5 of 365 days with no coverage-start field in the result (PROBE B). Nothing calls the seed "a year", but the contract lets any chart render 360 blank-as-zero days. Also the index is rewritten every run (`generated_utc`, PROBE 3) which clears the whole shard cache (history-window.mjs:113).

**3. FAIL risk — unbounded day shards, coupled to the live feed.** A real feature is 526 bytes compact (EV/sizing_and_load.txt): 137-char product name in the id plus ~250 bytes of constant text. 100k flashes/day = 52.6 MB (> GitHub's 50 MiB warning), 200k = 105 MB (> 100 MiB block: push rejected). Met Office counted >30,000 ground strikes in one night in June 2025, mostly over the sea (inside this −11…3°E box); LI counts total lightning (IC+CG) at 70–95% detection efficiency, so 10^5 flashes/day is the planning case. PR workflow commits feed+archive in one commit (update-lightning.yml diff, hunk at lines 38-48) and `archive_observations` runs before the feed is written (collect.py diff lines 210-221 vs 229): an oversize push or any `ValueError` from history.py:154/176/181/186/188 stalls the 7-day live feed as well. Pruning (history.py:229-231) frees the checkout, not the repository; every 3-hourly rewrite of a growing day file is a new blob in history. Year totals at today's encoding: 0.16 GB (300k flashes) to 1.58 GB (3M); GitHub recommends <1 GB, <5 GB strongly.

**4. Scalability of full re-validation.** history.py:167-190 re-reads and re-validates every shard every run: 16.6 µs and ~1.5 KB RSS per archived feature (240k-feature fixture: 4.0 s, +374 MB). 1M flashes → 17 s/1.6 GB; 3M → 50 s/4.7 GB, plus a full-tree checkout every run. Not fatal on a 16 GB runner, but wrong shape: only touched days should be parsed; others verified by `bytes`/`sha256` from the index.

**5. Reader mid-write race is real and undetected.** raw.githubusercontent.com: `cache-control: max-age=300`, gzip (215 KB → 12.9 KB), CORS `*` (EV/raw_headers.txt). Index and shards are separate URLs with independent 5-min edge caches; `cache:'no-store'` (history-window.mjs:106) bypasses only the browser cache. The day loader checks schema/type/date_utc only (lines 123-126), not `count`. PROBE A: index says 3, stale shard has 2 → no error, label "2 shown of 2 archived". The index lacks `bytes`/`sha256` (the V6 reference index the PR cites has `rows` and `sizeBytes`). GitHub applies undisclosed unauthenticated rate limits to raw downloads (changelog 2025-05-08): readers must degrade to "unavailable", never to zero. PROBE C: a 30-day detail request with 3.1M indexed flashes fires 30 shard downloads with no byte budget (~1.6 GB today).

**6. PASS — optical flashes are never labelled ground strikes.** collect.py:59-66 sets `raw_tech` "EUMETSAT optical flash (not a confirmed ground strike)", `status` "Satellite detection", `observation_kind` "optical_lightning_flash"; 408/408 features carry all three; the only "strike" strings in the file are the 409 negations; zero "cloud-to-ground" (EV/geojson_inspection.txt). history.py:64 and history-window.mjs:65,161 enforce `observation_kind`; `validateIndex` requires the "not ground strikes" sentence. Weakness: free text is not validated (PROBE 7 archived a feature whose `raw_tech` was tampered to "confirmed ground strike") — low.

**7. PASS with caveats — IDs, timestamps, dedup.** id = `<product name>:<NetCDF row>` (collect.py:53), deterministic per product file; 408 unique ids, 116 products, all 10-minute slots aligned at :09 s, `OPE … N__O_<slot>_0000`, no reissued slot, no near-duplicate flash (EV/product_slots.txt). Dedup by id in `assemble` (collect.py:170) and archive (history.py:161,197-198); re-ingestion idempotent (PR test + PROBE). Caveats: the row index is a position in the full-disc array (max 27,904 seen); a reprocessed/reissued product carries a new processing time in its name, so the same flash would get a new id and be double-counted on backfill. The LFL product has a `flash_id` variable (EUMETSAT LI L2 PUG Table 3) that collect.py ignores; `flash_filter_confidence` is also ignored although the LI validation paper lists false-flash sources (stray light, read-out noise, debris). `iso_utc` truncates a trailing zero for non-fractional string input (`12:32:20` → `12:32:2Z`, EV/probe_iso_utc.txt) — latent only; the cftime path always carries `.%f`. Timestamps are stable: ms precision, all 24-char `Z` strings, [start,end) filtering and UTC-day assignment correct (PROBE 6).

**8. PASS — no fabrication or interpolation; but failures leave no trace.** No code path synthesises points; masked/invalid rows are skipped (collect.py:91-100); coordinates rounded to 6 dp; zero products raises (collect.py:132-133,143-144) and nothing is written; a failed run keeps the previous file. Runs 1–2 on 22 Oct failed (EV/actions_runs.txt) and the data shows no record: no `last_attempt_utc`, `last_error` or failure count; staleness is only inferable from `query_end_utc`.

**9. 40k cap ordering is correct.** PROBE 4: 40,005 incoming → archive 40,005, feed the latest 40,000, `total_before_display_cap` 40,005; the client slices the newest 40k and sets `truncated` (history-window.mjs:168). The archive seed is the already-capped feed, acceptable for the seed only.

**10. EUMETSAT source truth.** LI FOV ±80° N–S/±75° E–W, flash detection efficiency 70% (day)–95% (night), mean 87.4%, >80% to ~70°N; 4.5 km at nadir, ~7 km over central Europe, coarser at 60°N; pre-operational dissemination since July 2024; ~14 outage days in the validation period (egusphere-2026-3177). Collection EO:EUM:DAT:0691 serves 10-minute "ARC" packaging, 144 products/day, each available only after slot end + processing (observed <6 min). Seed flashes reach 61.06°N and the west edge (−10.9998°), so the box is fully inside usable coverage, but daytime undercount is systematic. Missing EUMETSAT slots are source gaps: unknown, not zero.

### Concrete thresholds
- **Encoding**: move constant properties to shard `metadata.feature_defaults`; id `<sensing_start_yyyymmddhhmmss>:<flash_id>` (fallback row); keep `time_utc`, add `confidence`. Target ≤160 B/flash (measured 153 B).
- **Shards**: day file target ≤8 MiB, hard ≤24 MiB; above target split hourly `days/YYYY/MM/DD/HH.json` listed in the index; never >45 MiB.
- **Index per day**: `date, status∈{observed_flashes, observed_none, partial, unknown}, count|null, slots_examined (0–144), coverage_fraction, first/last_observation_utc, paths[], bytes, sha256, sealed`. Top level: `coverage_start_utc, last_successful_scan_end_utc, last_attempt_utc, last_error, consecutive_failures, products_examined_total, seed_note`.
- **Rendering per range**: detail only if Σcount ≤ 40,000 desktop / 15,000 mobile and Σbytes ≤ 25 MB raw; else daily-status overview; always "N shown of M".
- **Staleness**: warn when now − `last_successful_scan_end_utc` > 6 h; "stale" > 12 h; "collection stopped" > 24 h.
- **Collector**: hourly cron; window = max(6 h, now − last_successful_end + 30 min) capped 48 h; record examined product slots; on failure write `data/status.json` in an always-run step.

### Backfill proof protocol (genuine EUMETSAT products only)
1. Idempotency: re-download three already-ingested products (e.g. 21 Oct slot 0076) → features must equal archived ones byte-for-byte.
2. Reissue check: per sensing window exactly one product; if two, compare flash sets and fix the dedup key before any backfill.
3. Day completeness: fetch 23–25 Oct as whole UTC days → `products_examined` = 144 each; every new flash must fall inside a reconstructed gap (EV/scan_windows_analysis.txt); no existing id changes; day status becomes observed_*.
4. Bounded year: 365 × 144 = 52,560 products in 48 h dispatches (288 products, ~30 min each, cf. run 3: 22:41→23:11), ~183 dispatches, one at a time; any run with <288 products logs the missing slots as source gaps; stop on first discrepancy.
5. Only days with `slots_examined` = 144 may be called complete; nothing else is interpolated or back-dated.

## Objections to other lanes
- **Transport**: the live feed stays `.geojson` and will be hijacked by `legacyStem()`; the PR's `.json` shards avoid this, so the implant should read index+shards (and a `.json` mirror of the 7-day feed), never a `.geojson` URL. MapLibre loads a GeoJSON `data:` URL inside its worker, bypassing the main-thread `window.fetch` patch — prove both paths. "Refreshed" labels must come from `generated_utc`, not fetch time (5-min CDN).
- **UX**: never draw zero bars for `unknown`/`partial` days; show coverage start; a 12-month view over a 5-day archive must say so numerically.
- **Lead's facts**: "last 7 days seed" is 4 days of flashes with half the hours scanned.
- **Builder**: PR #1 is not mergeable as-is (findings 2–5); keep feed and archive in separate commits, feed first.

## Recommendation for the smallest additive integration
Fix the lightning repo before touching GridAtlas: (1) hourly cron with self-healing lookback and per-slot coverage recording; (2) index v2 with per-day status/coverage/bytes/sha and a failure status file; (3) compact encoding with shard caps, archive commit decoupled from the feed; (4) GridAtlas implant fetches only `.json` paths and honours status, byte budget, skew detection and staleness thresholds above. Backfill the seed days first (protocol step 3) as the acceptance proof.

## Verdict
**FAIL** — code and tests are sound, but the archive contract cannot tell unknown from zero per day, rides a collector that has missed ~46% of hours, and has unbounded shards coupled to the live feed.
